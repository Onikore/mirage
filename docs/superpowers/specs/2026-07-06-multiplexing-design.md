# Мультиплексирование стримов поверх одной сессии — design

## Проблема

README, roadmap: «Сейчас одно TCP-соединение на один запрос. Добавить
stream_id в кадры, гонять все стримы по одной сессии.» Каждый SOCKS5-запрос
клиента сегодня — это новое TCP-соединение + новое Noise-рукопожатие с
нуля. Дорого и заметно (много похожих коротких TLS-подобных хендшейков с
одного IP подряд).

## Решение

Слой `Session`/`Stream` НАД уже существующим `*protocol.SecureConn` —
`SecureConn` не меняется вообще, `Session` просто оборачивает его как
`io.ReadWriteCloser`.

Формат кадра мультиплексора (внутри уже расшифрованного потока
`SecureConn`): `[u32 streamID][u8 type][u16 len][payload]`. Три типа:
`OPEN` (payload — адрес цели, тем же форматом, что уже даёт
`socks.EncodeAddr`/`socks.ReadAddr`), `DATA` (payload — прикладные байты),
`CLOSE` (без payload).

**Проверено прототипом** (голый `net.Pipe`, без реального Noise) до
переноса в проект: 5 параллельных стримов поверх одного соединения,
каждый со своими данными — корректно доехали каждый до своего адресата,
без переползаний между стримами; `-race` чист; закрытие одного стрима
корректно даёт `io.EOF` при последующем Read.

## Архитектура

- **`internal/protocol/mux.go`** (новый файл) — `Session` (одна на
  TCP-соединение, поднимается над `*SecureConn` через `NewSession`),
  `Stream` (реализует `io.ReadWriteCloser`, один на логический
  запрос). `Session.Open(payload []byte) (*Stream, error)` — клиент
  открывает новый стрим. `Session.Accept() (*Stream, []byte, error)` —
  сервер блокируется до следующего открытого клиентом стрима, получает
  OPEN-payload как есть (адрес декодирует уже вызывающий код через
  `socks.ReadAddr`, mux.go про адреса ничего не знает — чистая
  мультиплексация, не смешана с адресной семантикой).
  Одна фоновая горутина на сессию (`readLoop`) читает кадры и
  раздаёт по стримам; запись сериализована мьютексом (`wmu`) — это ровно
  то, что требует контракт `net.Conn` (один читатель, один писатель
  одновременно), так что дополнительная синхронизация на уровне
  `SecureConn` не нужна.
- **`cmd/mirage/main.go`** — клиент: один хендшейк на процесс (не на
  запрос), `Session` поднимается один раз, каждый SOCKS5-accept — это
  `session.Open(...)`, а не новый `net.Dial`+`ClientHandshake`. Сервер:
  после успешного `ServerHandshake` (это по-прежнему один раз на TCP-
  соединение — rate-limit/anti-replay проверяют именно этот момент, не
  меняются) сервер вместо одного `readAddr`+`relay` крутит
  `session.Accept()` в цикле, на каждый стрим — свой `net.Dial` до цели и
  свой `relay(stream, remote)` в отдельной горутине.

## Что упрощено (сознательно, ponytail)

- Нет реального flow control — при переполнении буфера принятых-но-
  непрочитанных стримов (`acceptCh`) новые OPEN тихо дропаются. На
  практике это означает: если приложение открывает пачку запросов, а
  локальный код не успевает их вычитывать, лишние теряются вместо
  постановки в очередь. Апгрейд — протокольный сигнал backpressure,
  не делали.
- Обрыв сессии (потеря TCP-соединения до сервера) не переподключается
  автоматически — все активные и будущие стримы клиента начинают
  ошибаться, процесс клиента нужно перезапустить. Соответствует общему
  статусу проекта (не боевой инструмент, см. README «Дисклеймер»).

## Тестирование

`internal/protocol/mux_test.go`: конкурентный round-trip нескольких
стримов (перенос уже проверенного прототипа), закрытие стрима -> EOF,
`-race` чист. Плюс ручная проверка на реальных бинарниках: несколько
параллельных `curl` через один и тот же `mirage client` процесс — в логе
сервера должен быть один хендшейк и несколько `tunnel ->` на разные
цели через один и тот же TCP-коннекшен.
