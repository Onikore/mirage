# Server hardening: panic recovery + global session cap — design

## Проблема

Пользователь сформулировал приоритет прямо: «чтобы сервер не отваливался и
его не заблокировали». Два конкретных, независимо найденных риска:

1. **Ни один обработчик соединения не защищён от паники.** Паника в Go
   убивает весь процесс, а не только свою горутину. Парсеры сетевого
   формата (`servhello.go`, `camouflage.go`) вручную режут байты
   недоверенного ввода по индексам — один аномальный пакет от зонда,
   сканера или просто битого клиента в теории может обрушить весь сервер и
   разом оборвать все чужие активные сессии. Сам факт падения (и
   последующий рестарт систем) — тоже потенциальный сигнал для стороннего
   наблюдателя, не только потеря соединений.
2. **Нет глобального лимита одновременных сессий.** Есть per-IP
   rate-limit на попытки хендшейка (`ratelimit.go`), но ничто не мешает
   большому количеству РАЗНЫХ IP (или одному IP, действующему медленнее
   лимита) держать неограниченное число одновременно живых сессий,
   исчерпывая память/файловые дескрипторы процесса.

## Решение

### 1. Panic recovery — `goSafe`

Новый файл `cmd/mirage/safety.go`:

```go
package main

// safety.go — goSafe запускает fn в горутине с recover(): паника в одном
// соединении/стриме не должна убивать весь процесс и обрывать все чужие
// активные сессии. Использовать вместо голого `go fn()` на любой горутине,
// разбирающей сетевой ввод от клиента (см. точки вызова в main.go,
// quic_server.go).

import (
	"log"
	"runtime/debug"
)

func goSafe(name string, fn func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("recovered panic in %s: %v\n%s", name, r, debug.Stack())
			}
		}()
		fn()
	}()
}
```

Оборачиваем ВСЕ точки спавна горутин на пути необработанных сетевых данных
(recover() ловит панику только в своей же горутине, поэтому нужно на каждой
точке спавна отдельно, а не один раз снаружи):

- `cmdServer`: `go serveConn(...)` → `goSafe("serveConn", func() { serveConn(...) })`
- `cmdServer`: `go serveQUICConn(...)` → аналогично
- `serveConn`/`quic_server.go`: `go serveStream(...)` → аналогично
- `relay()` (main.go) и `relayStats()` (stats.go): обе внутренние горутины
  `go func() { io.Copy(...) }()` — они уже отдельные горутины, recover() в
  вызывающей функции их не поймает, значит оборачиваем каждую индивидуально.

Клиентские горутины (GUI/CLI) сознательно не трогаем в этой итерации —
пользователь просил именно про сервер; крах клиента у пользователя себя же
и задевает, не чужие сессии.

### 2. Глобальный лимит сессий

Новый флаг `-max-conns` на сервере (по умолчанию `1000`, `int`).

Переиспользуем уже существующий атомарный счётчик `statActiveConns` из
`stats.go` вместо нового поля — он и так растёт на успешном хендшейке и
падает на завершении сессии (`serveConn` уже делает
`atomic.AddInt64(&statActiveConns, 1)`/`defer ... -1`). Проверка лимита —
рядом с уже существующей `il.allow(host)`, ДО крипто-работы:

```go
if !il.allow(host) || atomic.LoadInt64(&statActiveConns) >= int64(*maxConns) {
    fallback(c, nil, dest)
    return
}
```

Тот же принцип, что уже описан в комментарии `ratelimit.go`: превышение
лимита уходит в тот же `fallback()`, что и обычный зонд или rate-limited
IP — снаружи неотличимо «сервер не ответил конкретно этому», а не «сервер
перегружен». Раздельное поведение само стало бы фингерпринтом.

Обе функции (`serveConn`, `serveQUICConn`) получают новый параметр
`maxConns int`, прокидываемый из `cmdServer` (`*maxConns` из флага) в оба
вызова -- сигнатуры:

```go
func serveConn(c net.Conn, privs *privSet, ps *pskSet, dest string, rc *protocol.ReplayCache, il *ipLimiter, padding bool, maxConns int)
func serveQUICConn(qc *quic.Conn, privs *privSet, ps *pskSet, dest string, rc *protocol.ReplayCache, il *ipLimiter, maxConns int)
```

В `serveQUICConn` -- ровно та же объединённая проверка, что и в TCP-пути,
на месте уже существующего `il.allow` в начале функции:

```go
if !il.allow(host) || atomic.LoadInt64(&statActiveConns) >= int64(maxConns) {
    qc.CloseWithError(1, "rate limited")
    return
}
```

(как уже делает существующий код при неудачном хендшейке; полноценного
fallback-проброса для QUIC как раз нет и это не новая асимметрия, она уже
существует в коде).

### Попутный фикс: QUIC-сессии не считаются в `statActiveConns`

Сейчас инкремент/декремент `statActiveConns` есть только в `serveConn`
(TCP). `serveQUICConn` его не делает вообще — значит и статистика, и (без
этого фикса) новый глобальный лимит видели бы только TCP-нагрузку.
Добавляем те же `atomic.AddInt64(&statActiveConns, 1)`/`defer ... -1` в
`serveQUICConn` сразу после успешного хендшейка, симметрично TCP-пути.

## Что не делаем в этой итерации

- Автоматический расчёт лимита от доступной памяти — отклонено в пользу
  фиксированного флага (см. согласование с пользователем).
- Настоящий resource-quota на сессию (лимит памяти/трафика на одного
  клиента) — отдельная задача, не про «сервер падает целиком».
- Fail2ban-style автоматическая блокировка агрессивных IP на уровне
  firewall — за пределами этой итерации, уже есть per-IP rate-limit.
- «Настоящий» fallback-проброс для QUIC (полноценная имитация реального
  сайта, а не просто закрытие соединения) — существующий, отдельный от
  этой задачи пробел.
- Recovery для клиентских (GUI/CLI) горутин — вне заявленного приоритета
  пользователя («сервер», не клиент).

## Тестирование

- Юнит-тест на `goSafe`: паникующая функция не должна прерывать вызывающий
  тест и должна дать возможность убедиться, что горутина завершилась (или
  что процесс просто продолжает жить) — например, через канал-сигнал
  после `recover()`.
- Юнит-тест на лимит: с помощью прямого управления `statActiveConns`
  (или мока) проверить, что при значении ≥ `-max-conns` `serveConn` уходит
  в `fallback` до вызова `ServerHandshake` (не тратит крипто-работу).
- Ручная проверка на реальных бинарниках: поднять сервер с малым
  `-max-conns` (например, 2), открыть 2 туннеля, убедиться что третье
  подключение получает fallback-поведение (соединяется, но получает
  трафик `-dest`, а не настоящий туннель), затем закрыть один туннель и
  убедиться, что третье подключение (новая попытка) снова проходит.
- Ручная проверка паники: временно внести управляемую панику в тестовой
  сборке (или через существующий баг, если найдётся) в `serveStream`,
  убедиться что процесс не падает, в логе появляется
  `recovered panic in serveStream: ...`, остальные активные сессии
  продолжают работать.
