# Client auto-reconnect — design

## Проблема

Клиент (`mirage client` и оба GUI — `gui_windows.go`, `gui_linux.go`) делает
одно рукопожатие на процесс и держит один статический `*protocol.Session`
(см. `cmd/mirage/main.go`, `runClientListener`/`clientConn`). Если базовое
TCP-соединение клиент↔сервер обрывается (простой/NAT-таймаут, перезапуск
сервера, сетевой сбой) — воспроизведено живьём в этой же сессии работы
(`broken pipe` после ~5 часов простоя) — сессия молча умирает, и все
последующие локальные SOCKS5-запросы падают с ошибкой, пока пользователь не
перезапустит `mirage client` (CLI) или не нажмёт Disconnect/Connect (GUI).
Осознанно не делали раньше (см. `DEPLOY.md`) — теперь делаем.

## Решение

### Что НЕ трогаем

`internal/protocol/mux.go` (`Session`, `Stream`) — без изменений в логике.
Мультиплексирование, кадры, backpressure — всё как есть, это самый
проверенный (3 раунда конкурентных багфиксов) и деликатный файл проекта.

### Один аддитивный публичный метод в protocol

Сейчас `Session.closed` (канал) и `Session.closeErr` — приватные поля,
наружу не торчат, хотя сигнал уже существует (`shutdown()` закрывает
`closed`, когда `readLoop` получает ошибку чтения). Открываем его по
образцу `context.Context`, ничего не меняя в существующей логике:

```go
// Done возвращает канал, который закрывается, когда сессия умерла
// (обрыв соединения, чтение вернуло ошибку) — тот же сигнал, которым
// уже пользуется внутренний shutdown().
func (s *Session) Done() <-chan struct{} { return s.closed }

// Err возвращает причину закрытия сессии (nil, пока сессия жива).
func (s *Session) Err() error {
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.closeErr
}
```

### `sessionHolder` — новый тип в `cmd/mirage/reconnect.go`

Тонкая обёртка между CLI/GUI и протоколом:

```go
type sessionHolder struct {
	mu       sync.Mutex
	sess     *protocol.Session // nil, пока идёт передозвон
	dial     func() (*protocol.Session, error)
	onStatus func(string)
	stopCh   chan struct{}
}
```

- `newSessionHolder(initial *protocol.Session, dial func() (*protocol.Session, error), onStatus func(string), minBackoff, maxBackoff time.Duration) *sessionHolder`
  — принимает уже установленную первую сессию (первый коннект остаётся
  fail-fast, как сейчас — `log.Fatal` в CLI, показ ошибки в GUI, вне этого
  компонента) и запускает фоновую горутину. `minBackoff`/`maxBackoff` —
  явные параметры (не хардкод внутри) специально ради теста: CLI/GUI
  передают боевые 1с/30с, юнит-тест — единицы миллисекунд.
- `(*sessionHolder).Current() *protocol.Session` — текущая сессия под
  мьютексом, либо `nil`, если прямо сейчас идёт передозвон.
- `(*sessionHolder).Stop()` — останавливает цикл ретраев и закрывает
  текущую сессию (используется в GUI Disconnect).

Фоновая горутина: ждёт `<-sess.Done()` → зовёт `onStatus` с причиной
(`sess.Err()`) → цикл: растущая пауза (1с, 2с, 4с, ... потолок 30с) →
`dial()` → при ошибке `onStatus` с номером попытки и ошибкой, снова пауза;
при успехе — сохраняет новую сессию под мьютексом, зовёт `onStatus`
("reconnected"), возвращается к ожиданию `<-newSess.Done()`. Ретраи не
ограничены по количеству — только явный `Stop()` останавливает цикл.
Пока сессии нет (`sess == nil`), `Current()` отдаёт `nil` — вызывающий код
(`clientConn`) должен сразу закрыть локальное соединение, не ждать.

`dial` — замыкание, которое собирает вызывающий код (CLI или GUI),
инкапсулирует `net.DialTimeout` + `protocol.ClientHandshake` +
`protocol.NewSession` + (если включён) `StartPadding` с уже известными
`server`/`pub`/`psk`/`sni`/`padding`. `sessionHolder` намеренно не знает
про сеть/хендшейк — только про жизненный цикл сессии. Это даёт чистый
юнит-тест: в тесте `dial` — фейковая функция на `net.Pipe`, без реального
хендшейка.

### Интеграция

- `clientConn(c net.Conn, h *sessionHolder)` (был `sess *protocol.Session`):
  `sess := h.Current(); if sess == nil { c.Close(); return }`, дальше как
  раньше.
- `runClientListener(ln net.Listener, h *sessionHolder)` — та же сигнатура
  паттерна, просто пробрасывает `h` вместо `sess`.
- `cmdClient`: первый dial+handshake остаётся как есть (fail-fast), потом
  `h := newSessionHolder(sess, dialFunc, onStatus)`, `onStatus` для CLI —
  `log.Printf`.
- `gui_windows.go` / `gui_linux.go`: `connect()` вместо прямого
  `runClientListener(ln, sess)` создаёт `sessionHolder` с `onStatus`,
  обновляющим статус-лейбл; `disconnect()` зовёт `h.Stop()` вместо прямого
  `sessConn.Close()`.

### Кроссплатформенный нюанс GUI-потоков

И `lxn/walk`, и Fyne ожидают, что виджеты трогают из UI-горутины. Фоновая
горутина `sessionHolder` дёргает `onStatus` из СВОЕЙ горутины — GUI-обёртки
должны маршалить обновление на UI-поток:
`gui_windows.go` — через `mw.Synchronize(func(){ ... })` (walk);
`gui_linux.go` — через `fyne.Do(func(){ ... })` (доступно в используемой
версии `fyne.io/fyne/v2` — v2.7.4, проверить в реализации). Без этого —
потенциальная гонка по данным виджета, не просто визуальный баг.

## Что НЕ делаем в этой итерации

- Не трогаем поведение самого первого коннекта (см. согласованное решение
  выше) — только уже установленная сессия подлежит автопереподключению.
- Не буферизуем/не откладываем новые локальные SOCKS5-подключения на время
  реконнекта — сразу ошибка (согласовано), без очереди и без таймаутов
  ожидания.
- Не ограничиваем число попыток переподключения — бесконечно, до ручного
  Disconnect/остановки процесса (согласовано).
- Не переносим уже открытые (до обрыва) `Stream` в новую сессию — старые
  локальные TCP-соединения, привязанные к старым стримам, штатно получают
  EOF при обрыве сессии (уже сделано в mux.go, shutdown() закрывает
  readCh всех стримов) и завершаются сами; новые запросы после реконнекта
  идут уже через новую сессию/новые стримы.

## Тестирование

- Юнит-тест `sessionHolder` (`cmd/mirage/reconnect_test.go`): фейковый
  `dial` на `net.Pipe` — первая сессия «умирает» (закрыть один конец pipe),
  `dial` возвращает ошибку N раз подряд, затем успех; проверить, что
  `Current()` возвращает `nil` в промежутке и корректную новую сессию
  после успеха, и что `onStatus` вызывался на каждом шаге. Backoff в тесте
  — с укороченными интервалами (внедряемый параметр, а не хардкод 1с/30с),
  чтобы тест не занимал реальные секунды.
- Ручная проверка на реальных бинарниках (CLI и оба GUI): установить
  сессию, оборвать её со стороны сервера (`systemctl stop mirage` на VPS
  или просто убить процесс), подождать несколько секунд, поднять сервер
  обратно (`systemctl start mirage`), убедиться, что клиент сам
  восстановился (статус/лог показывает reconnect, новый SOCKS5-запрос
  проходит) без ручного перезапуска клиента.
