## 2026-07-07 — Клиентское автопереподключение (обе GUI через `sessionHolder`)

**Что делали:** закрыли последнюю явную оговорку из DEPLOY.md («сессия
оборвалась — нужен перезапуск `mirage client`»): клиент (CLI и обе GUI,
Windows/walk и Linux/Fyne) теперь сам переустанавливает сессию с растущей
паузой, если она умирает уже после установки. 4 задачи через
subagent-driven-development: Task 1 — `Session.Done()/Err()/Close()` в
`internal/protocol` (сигнал смерти сессии наружу пакета); Task 2 —
`sessionHolder` в новом `cmd/mirage/reconnect.go` (растущая пауза 1с →
потолок 30с, удвоение, без ограничения по числу попыток) + `dialSession`
(общий код первого коннекта и передозвона); Task 3 — `cmd/mirage/main.go`
(CLI-клиент) переведён на `sessionHolder`; Task 4 (эта запись) — обе GUI
переведены на тот же `sessionHolder`, ручная проверка, документация.

**Что получилось:**
- Первый коннект (старт процесса/нажатие Connect в GUI) остаётся
  fail-fast, без единой попытки повтора — опечатка в адресе/ключах
  проявляется сразу, а не тонет в фоновых ретраях. `sessionHolder`
  включается только ПОСЛЕ того, как первая сессия уже установлена.
- Пока идёт передозвон, `sessionHolder.Current()` возвращает `nil`, и
  `clientConn` сразу отказывает новому локальному SOCKS5-подключению
  вместо того, чтобы держать его в ожидании (см. design spec, Global
  Constraints) — то же поведение что у CLI, что у обеих GUI, потому что
  все трое зовут один и тот же `runClientListener(ln, h)`.
- `sessionHolder.Stop()` не блокируется на активной попытке `dial()` —
  критично для GUI Disconnect, который иначе замирал бы на весь текущий
  таймаут дозвона; `run()` сам замечает `stopCh` и закрывает только что
  установленную (но уже никому не нужную) сессию сразу после возврата из
  `dial()`.
- Обе GUI (`gui_windows.go`, `gui_linux.go`) получили идентичную правку:
  вместо прямого `net.DialTimeout`+`protocol.ClientHandshake`+
  `protocol.NewSession`+сырого `sessConn io.Closer` — `dialSession` на
  первый коннект и `holder *sessionHolder` на всё дальнейшее, статус
  переключений (`session died: ...`, `reconnect attempt N failed: ...`,
  `reconnected`) промаршален на UI-поток каждого тулкита
  (`mw.Synchronize` у walk, `fyne.Do` у Fyne) — иначе гонка с рендером
  окна из фоновой горутины `sessionHolder.run()`.
- Полная перепроверка: `go build ./...`, `go vet ./...`, `gofmt -l .`, `go
  test ./... -race` — чисто; отдельно `GOOS=windows GOARCH=amd64
  CGO_ENABLED=0 go vet ./...` и кросс-сборка `mirage-gui.exe`
  (`-ldflags="-H windowsgui"`) — подтверждена как валидный PE32+ через
  `file`.
- **Ручная проверка (без VPS — self-contained loopback):** т.к. в этой
  среде нет SSH-доступа к задеплоенному VPS, вместо него поднят
  локальный `mirage server` на свежем порту (127.0.0.1:19443, тот же
  бинарник, тот же код) — это ровно тот же `dialSession`/`sessionHolder`
  путь, разница только в адресе сервера. Реальный CLI-клиент
  (`mirage client`) подключён к нему; `curl --socks5-hostname` через
  туннель → `200`. Затем реальный `kill` серверного процесса (не просто
  остановка — TCP RST/EOF, которое клиент фактически видит на чтении):
  лог клиента показал `session died: EOF -- reconnecting`, затем 4
  попытки с растущей паузой (`connection refused`, ~1с/2с/4с/8с), сервер
  поднят заново с теми же ключами/портом → `reconnected`, БЕЗ единого
  перезапуска клиентского процесса. Повторный `curl` сразу после —
  снова `200`. GUI проверили частично: реальное окно `gui_linux.go`
  открывается и рендерится на X-дисплее (подтверждено), но синтетический
  клик Connect не удалось довести до GLFW-цикла Fyne (нет xdotool/прав),
  поэтому полный клик-тест через кнопку не делали. Вместо этого отдельной
  standalone-программой на том же Fyne v2.7.4 проверили именно GUI-
  специфичный участок, который CLI-тест не покрывает: обновление лейбла
  через `fyne.Do` из фоновой горутины (ровно паттерн `setStatus`/`onStatus`)
  — прогон на живом дисплее отработал без паники, лейбл дошёл до значения
  `reconnected`. Сам реконнект-путь идентичен проверенному CLI. Полный
  живой клик-тест обеих GUI (особенно walk/Windows) всё же стоит сделать
  ручной проверкой у оператора среды.

**Что не получилось / пришлось поправить:**
- Известный (принятый) trade-off, не баг: если `Disconnect`/`Stop()`
  случается ровно в момент, когда фоновый передозвон уже получил новую
  сессию от `dial()`, но ещё не опубликовал её — эта сессия открывается
  и тут же закрывается (`newSess.Close()` в `run()`), а не остаётся
  никогда не открытой. Безвредно (соединение живёт доли секунды и
  корректно закрывается), но стоит держать в голове при чтении логов
  сервера — короткое TCP-соединение без единого запроса сразу после
  Disconnect может быть этим случаем, а не сканером.
- Первая проверка PID'ов тестового сервера/клиента через `$!` в bash
  сбивала с толку: `nohup ... &` внутри обёртки Bash-инструмента (`bash
  -c 'source snapshot.sh && eval ...'`) возвращает PID промежуточной
  подоболочки, а не самого фонового процесса — `kill` по нему не глушит
  реальный `mirage-recon server`/`client`. Поправился на `pgrep -af
  mirage-recon` для поиска настоящих PID перед `kill`.

**Коммиты:** Task 1 (`Session.Done/Err/Close`) — `ac64e0f`; Task 2
(`sessionHolder`, `reconnect.go`) — `79b4c8c` + `e25882b` (гонка
публикации после Stop) + `cb183af` (детерминированный тест-сид); Task 3
(CLI wiring) — `7fa2b0a`; Task 4 (обе GUI + докс, эта запись) — см.
следующий коммит. Всё в ветке `feature/client-auto-reconnect`.

## 2026-07-06 — Chameleon shaping: общая padding-обфускация (mux.go, `-padding`)

**Что делали:** по запросу продолжить свармом — следующий пункт роадмапа.
Явно обсудили с пользователем масштаб ДО дизайна: точное соответствие
профилю реального HTTP/3-трафика невозможно без настоящих захваченных
данных (их нет), договорились на честную общую обфускацию тайминга/
размеров вместо театра. Один новый тип кадра (`framePadding`) в уже
существующем формате mux.go, `Session.StartPadding(...)` — необязательный
фоновый цикл, шлёт кадр-шум случайного размера после случайного джиттера,
пока сессия жива. Флаг `-padding` на `server`/`client`, по умолчанию
выключен.

**Что получилось:**
- 2 задачи через subagent-driven-development (Task 1 — добавление в
  mux.go, транскрипция уже проверенного дизайна, дешёвая модель; Task 2 —
  CLI-обвязка, интеграционная работа, модель посильнее), ревью каждой —
  отдельным агентом. Обе одобрены без замечаний с первого раза — по
  контрасту с мультиплексом, здесь риск был низкий: механизм целиком
  переиспользует уже проверенную (и один раз уже починенную) плоскость
  `writeFrame`/`readLoop`, ничего нового по конкурентности не добавляет.
- Проверил заранее (до того, как это попало в план): `math/rand/v2` НЕ
  имеет пакетного `Read()` (в отличие от `math/rand` v1) — и, что важнее,
  выяснилось, что содержимое padding-кадра вообще не имеет значения:
  `writeFrame` пишет в уже AEAD-шифрованный `*SecureConn`, так что
  пассивному наблюдателю снаружи в любом случае виден только шифротекст,
  неотличимый от случайного независимо от plaintext. Упростил дизайн —
  padding заполняется нулями (`make([]byte, n)`), без лишнего кода на
  генерацию случайного содержимого. Также заранее проверил, что
  `rand.IntN(0)` паникует — подтвердил, что guard'ы `if max > min` в
  плане обязательны, а не перестраховка.
- Ручная проверка на реальных бинарниках: сессия с `-padding` на обеих
  сторонах простаивала ~12 секунд (несколько padding-кадров успели уйти
  в обе стороны при интервале 1-5с), затем обычный запрос всё равно
  дошёл корректно — padding не просочился в прикладной поток. Bad-PSK и
  raw-probe fallback отдельно перепроверены с `-padding` включённым — не
  задеты (padding стартует только после успешного рукопожатия).

**Что не получилось / пришлось поправить:** ничего существенного — самая
спокойная итерация в этой серии, ожидаемо, раз и дизайн, и механизм
реализации были заранее сужены до чего-то, что не рискует повторить
класс проблем мультиплекса.

**Коммиты:** mux.go padding (Task 1), CLI-флаг (Task 2) — ветка
`feature/chameleon-shaping`.

## 2026-07-06 — Windows-манифест: GUI падал при старте (TTM_ADDTOOL)

**Что делали:** по запросу — «посмотри гит, надо запустить протестить на
винде». Собрали `mirage.exe`/`mirage-gui.exe` нативно на Windows (Go
1.26.4), прогнали `go test ./...` и ручной loopback-прогон (keygen →
server → client → SOCKS5 → curl, HTTP/HTTPS/raw-probe fallback — всё как
в README). GUI (`cmdGUI`, `gui_windows.go`) падал паникой на
`(*Label).SetText` на nil-указателе при запуске без аргументов.

**Что получилось:**
- Настоящая причина — не сам nil pointer, а то, что его маскировало:
  `github.com/lxn/walk` требует встроенный Windows-манифест с
  зависимостью от Common-Controls v6; без него Windows грузит
  устаревший comctl32 v5, и создание тултипа падает с `TTM_ADDTOOL
  failed` уже на этапе `MainWindow.Create()`. `gui_windows.go` игнорировал
  ошибку `Run()` и безусловно звал `disconnect()`, которая трогала ещё не
  назначенные (`nil`) виджеты — отсюда и паника в трейсе.
- Добавили `cmd/mirage/mirage.exe.manifest` (тот же манифест, что в
  примерах lxn/walk) и `cmd/mirage/rsrc_windows_amd64.syso` — Go-линкер
  подхватывает `.syso` из папки пакета сам, без правок команды сборки.
  `.syso` сгенерирован `rsrc` (`github.com/akavel/rsrc`, с разрешения
  пользователя) — родной MS `cvtres.exe` даёт big-obj формат, который
  линкер Go отклоняет (`sectnum < 0`).
- `gui_windows.go` теперь проверяет ошибку `Run()` и не вызывает
  `disconnect()` на несуществующих виджетах, если окно не создалось.
- Заодно нашли и починили баг тестовой изоляции: `guiconfig_test.go`
  переопределял только `XDG_CONFIG_HOME`, а `os.UserConfigDir()` на
  Windows читает `%AppData%` — тесты реально писали/читали настоящий
  `%AppData%\mirage\gui-config.json` пользователя. Добавили
  `t.Setenv("AppData", dir)` в оба теста.
- Проверено после фикса: `go build`/`go build -ldflags="-H windowsgui"`/
  `go test ./...` чисто; оба `.exe` открывают окно (заголовок "Mirage",
  процесс не падает) — проверено и в рабочем дереве, и в отдельной копии
  репозитория (`master`), откуда пользователь запускал бинарники напрямую.

**Что не получилось / пришлось поправить:**
- Первая попытка встроить манифест — вручную через `mt.exe`
  (post-build) и `rc.exe`+`cvtres.exe` (Windows SDK/VS Build Tools, уже
  стоят на машине) — сработала как ad-hoc проверка через `mt.exe`, но
  `.syso`, собранный `cvtres.exe`, линкер Go не принял (`sectnum < 0`,
  big-obj формат). Пришлось спросить пользователя и установить `rsrc`
  отдельно — именно им пользуется сам lxn/walk в своих примерах.

## 2026-07-06 — Мультиплексирование стримов (mux.go)

**Что делали:** по запросу — «запусти сварм агентов, опус оркестратор,
делают младшие модели». `Session`/`Stream`-слой поверх `SecureConn`: один
Noise-хендшейк на процесс клиента вместо одного на запрос, несколько
логических потоков параллельно по одному TCP-соединению.

**Что получилось:**
- Дизайн проверен прототипом (`net.Pipe`, 5 конкурентных стримов, чисто
  под `-race`) до написания плана — тот же метод, что и во всех
  предыдущих итерациях.
- 2 задачи через subagent-driven-development: Task 1 (`mux.go` +
  тесты — транскрипция уже проверенного кода, дешёвая модель) и Task 2
  (вплетение в `cmd/mirage/main.go` — интеграционная работа, модель
  посильнее). Ревью каждой задачи — отдельным агентом, с конкретными
  вопросами по конкурентной корректности, а не общим «выглядит нормально».
- Ревью Task 2 само нашло реальный баг до мержа: `gui_windows.go` (GUI-
  клиент) заводил сессию на Connect, но никогда не закрывал её на
  Disconnect — утечка горутины (`readLoop`) и открытого соединения на
  каждый цикл подключения. Поправлено, перепроверено отдельным ревью.
- Rate-limit/анти-replay/fallback — не тронуты вообще: они охраняют
  хендшейк, который по-прежнему ровно один на TCP-соединение.

**Что не получилось / пришлось поправить (главное):**
- **Ручная проверка на реальном HTTP-трафике поймала гонку, которую не
  поймали ни юнит-тесты, ни `-race`.** 30 параллельных запросов через
  один процесс `mirage client` к двум разным целям — часть возвращалась
  обрезанной, при этом лог самого целевого сайта подтверждал, что тот
  честно принял и ответил на каждый запрос. Значит, потеря происходила
  внутри mux-слоя.
- Причина: `Stream.Read()` выбирал (`select`) между каналом с данными и
  общим сигналом закрытия, который использовался и для «удалённо
  закрыли», и для «локально бросили». Когда пир шлёт последний кусок
  данных и тут же закрывает стрим (ровно то, что делает обычный
  веб-сервер: ответил — закрыл соединение), `readLoop` кладёт данные в
  канал и тут же закрывает сигнал — последовательно, в одной горутине.
  Если `Read()` выполняет свой `select` уже после обоих событий, Go
  выбирает между двумя готовыми ветками психевдослучайно — примерно в
  половине случаев выбирался сигнал закрытия, и уже забуференные данные
  тихо терялись. Это гонка честности `select`, не гонка по памяти —
  поэтому `-race` её не видит в принципе.
- Первая попытка написать регрессионный тest через `net.Pipe` НЕ
  воспроизвела баг даже на заведомо старом коде — синхронная,
  небуферизованная природа `net.Pipe` держит `readLoop` в жёсткой
  синхронности с писателем, не давая гонке открыться. Только настоящий
  TCP (с буферизацией в ОС) даёт `readLoop` убежать вперёд потребителя
  настолько, чтобы гонка проявилась. Переписал тест так, чтобы напрямую
  конструировать нужное состояние (данные уже в буфере + сигнал закрытия)
  без сети и без расчёта на тайминг горутин — детерминированно.
- Исправление: развёл два разных сигнала по смыслу. Удалённый CLOSE
  закрывает канал с данными НАПРЯМУЮ — и делает это только `readLoop`,
  единственный писатель в этот канал, поэтому строго последовательно со
  своими же отправками (гонка невозможна структурно, не «мы надеемся»).
  Приходящие-но-непрочитанные данные поэтому гарантированно дочитываются
  до EOF (гарантия Go: закрытый буферизованный канал сначала отдаёт всё,
  что в нём есть). Локальный `Close()` сигналит через отдельный канал,
  которым `readLoop` никогда не занимается — гонка в этом случае
  приемлема (вызывающий сам решил не читать дальше), но она отдельная
  и больше не пересекается с «доставить всё, что прислал собеседник».
- Прежде чем считать фикс готовым — доказал, что новый тест реально ловит
  баг: прогнал тот же детерминированный сценарий против СТАРОГО дизайна
  в отдельной копии — 253 из 500 прогонов (~50%) потеряли данные, ровно
  как предсказывала теория. Против нового дизайна — 0 из 10×200 прогонов.
- Фикс отдельно проверен независимым ревью (не тем агентом, что писал
  исправление) — одобрено без замечаний.
- Ручная проверка повторена на исправленном бинарнике: 30 параллельных
  запросов к двум целям — все верны. Заодно замечено: клиент с неверным
  psk теперь падает СРАЗУ при старте процесса (лог `handshake: ... auth
  failed`, `log.Fatal`), а не при первом запросе — естественное следствие
  «один хендшейк на процесс», не регресс.

**Финальное ревью всей ветки** (opus, самая мощная модель — на архитектурные
проверки) нашло ещё один живой баг того же класса «незаметно под простыми
тестами и `-race`»: при переполнении очереди принятых-но-невычитанных
стримов (`acceptCh`, cap 16) новый стрим дропался, но уже был зарегистрирован
в карте сессии — заброшенный стрим никогда не принимается и не закрывается,
а когда его `readCh` (cap 64) забивается следующими DATA-кадрами, `readLoop`
блокируется навсегда, останавливая ВСЮ сессию, не только этот один запрос.
Поправлено: регистрация в карте — только при успешной постановке в очередь
приёма, не раньше. Плюс два мелких: `Stream.Write` теперь режет payload
крупнее 65535 байт на несколько кадров вместо молчаливой обрезки длины
(экспортированный тип, пусть сейчас недостижимо через `relay()`), и
уточнены операторские заметки в DEPLOY.md (rate-limit считает попытки
подключения, не запросы внутри уже открытой сессии; клиент теперь падает
сразу при недоступном сервере, автопереподключения нет).

**Коммиты:** mux.go core, main.go wiring, GUI session-leak fix, data-loss
race fix, final-review dropped-OPEN fix — все в ветке `feature/multiplexing`.

## 2026-07-06 — ServerHello-камуфляж (servhello.go)

**Что делали:** замаскировали msg2 (сервер→клиент) под минимальный
спецификационно корректный TLS 1.3 ServerHello, закрывая последний
задокументированный пробел из исходного roadmap-пункта 1.

**Что получилось:**
- Обнаружилось до всякого кода: uTLS — клиентская библиотека, у неё нет
  публичного Marshal() для ServerHello (только для ClientHello) — значит
  для сервера нужен свой, ручной конструктор. RFC 8446 §4.1.3 достаточно
  простой и стабильный, чтобы сделать это на голом stdlib без сторонней
  библиотеки — и JA3S-подобный фингерпринтинг серверов не так
  распространён, как JA3/JA4 по клиентам, так что byte-perfect соответствие
  конкретной реализации не требовалось, только валидная форма.
- ServerHello обязан эхом вернуть session_id клиента (TLS 1.3 требование)
  — `camouflage.go` раньше отбрасывал 16 из 32 байт client-side session_id
  (оставлял только tag1). Пришлось расширить `parseMimicClientHello`,
  вернув полный session_id — единственная правка в camouflage.go за всю
  историю этого файла (до сих пор он не менялся ни разу).
- Место для tag2 (16Б AEAD-тег): не в session_id ServerHello (его нужно
  честно эхо-вернуть) — решили отдельной "продолжающей" записью с
  content-type 0x17 (application_data), ровно как настоящий TLS 1.3
  сервер шлёт EncryptedExtensions/Certificate/Finished сразу вслед за
  ServerHello — снаружи (без ключей) неотличимо от непрозрачного
  шифротекста любой длины.
- Прототип build/parse round-trip проверен на голом stdlib до переноса в
  проект (тот же метод, что и для uTLS/Noise раньше).
- 3 новых теста (servhello_test.go) + полный прогон вживую: легитимный
  трафик, bad-psk fallback, raw-probe fallback — все три поверх новой
  двусторонней мимикрии ведут себя как раньше.

**Что не получилось / пришлось поправить:**
- Первая версия прототипа не собралась: `byte(0x1301)` — компилятор Go
  ловит переполнение константы ещё на этапе компиляции для нетипизированных
  констант без сдвига. Поправили на `byte(cipherSuite & 0xff)`.
- После переноса в проект `TestServerHandshakeRejectsReplay` подвис
  (таймаут 20с, deadlock) — тест читал ровно 48 фиксированных байт в
  ответ на msg1, а msg2 теперь переменной длины (ServerHello-запись +
  continuation-запись, ~148 байт). Сервер блокировался на `conn.Write`,
  ожидая, что кто-то дочитает оставшиеся байты. Поправили: тест теперь
  вызывает настоящий `parseMimicServerHello` вместо фиксированного чтения.
- Заодно удалили `hsMsgLen` — константа стала мёртвым кодом, раз обе
  стороны хендшейка больше не читают msg1/msg2 фиксированным блоком.

**Коммит:** `7feff81` (ветка `feature/clienthello-camouflage`).

## 2026-07-06 — Ротация ключей без остановки сервера

**Что делали:** `pskset.go` — набор одновременно валидных psk
(`atomic.Pointer[[][]byte]`), загрузка из файла (`-psk-file`, один hex-psk
на строку), горячая перезагрузка по `SIGHUP`. `serverHandshake` теперь
перебирает кандидатов из набора, пока один не подойдёт.

**Что получилось:**
- `-psk` (одиночный режим) и `-psk-file` (набор + ротация) можно
  комбинировать — оба объединяются в один набор; ничего не сломалось для
  существующего однопsk-workflow.
- Битый файл при перезагрузке не обнуляет доступ — ошибка логируется,
  старый набор остаётся действовать (fail-safe, не «опечатка = все
  отрезаны»).
- 8 новых тестов: парсинг файла (комментарии/пустые строки/неверная
  длина/пустой файл), атомарность `Store`/`Load`, и интеграционный тест
  «сервер с двумя ключами принимает клиента и со старым, и с новым psk».
- **Живая демонстрация на реальных бинарниках — то, ради чего всё
  делалось:** сервер запущен с `-psk-file`, содержащим только старый psk;
  клиент со старым работает, с новым — нет; дописали новый psk в файл,
  `kill -HUP <pid>` → лог «reloaded: 2 key(s) active» → оба клиента
  заработали; убрали старый psk из файла, снова `SIGHUP` → «reloaded: 1
  key(s) active» → старый клиент теперь отклоняется, новый по-прежнему
  работает. **Один и тот же PID сервера на протяжении всего теста** — ни
  разу не перезапускался.

**Что не получилось / пришлось поправить:**
- Первая попытка ручной проверки переменные `$OLDPSK`/`$NEWPSK` из одной
  bash-команды не увиделись в следующей (каждый вызов Bash-инструмента —
  отдельный процесс оболочки, состояние переменных не сохраняется между
  вызовами) — файл psks.txt получился пустым, сервер упал с «no psks
  found» ещё на старте. Поправили: сохранили сгенерированные psk в
  файлы в `/tmp` и подставляли через `$(cat ...)` в каждой последующей
  команде вместо переменных окружения.
- `server_priv` (в отличие от psk) в этой итерации НЕ ротируется — его
  смена всё ещё требует перезапуска сервера и новых `server_pub` у всех
  клиентов. README это теперь явно называет остающимся пробелом.

**Коммит:** `f8780e5` (ветка `feature/clienthello-camouflage`).

## 2026-07-06 — Per-IP rate-limit

**Что делали:** добавили `ratelimit.go` — per-IP token-bucket
(`golang.org/x/time/rate`, burst=5, доливка 0.5/сек) на входе в
`serveConn`, до какой-либо крипто-работы.

**Что получилось:**
- Превышение лимита уходит в тот же `fallback()`, что и обычный зонд —
  никакого отдельного «rate limited» поведения, которое само стало бы
  фингерпринтом.
- Чистка простаивающих IP-бакетов — та же ленивая схема, что в
  replay.go (полный проход по карте при каждой проверке, TTL 10 минут).
- 3 юнит-теста: burst проходит и блокирует дальше, доливка возвращает
  токен по расписанию, разные IP не мешают друг другу.
- Ручная проверка на реальных бинарниках: 8 параллельных SOCKS5-запросов
  через один и тот же клиент → ровно 5 получили `tunnel ->` в логе
  сервера, 3 остальных сразу ушли в `probe -> transparent proxy`
  (клиентские curl соответственно словили обрыв соединения); после паузы
  в 3с новый запрос снова прошёл — доливка токенов подтверждена вживую,
  не только в тесте.

**Что не получилось / пришлось поправить:**
- Ничего существенного — оценка констант (burst/доливка) сделана на
  глаз для одиночного личного использования, не нагрузочно протестирована
  под реальным трафиком нескольких клиентов с одного NAT (см. риск ниже).

**Известный риск, который стоит держать в голове:** лимит считается по
IP клиента. Несколько легитимных пользователей за одним NAT/CGNAT будут
делить один бакет — при большом числе клиентов за общим IP это может
начать резать легитимный трафик раньше, чем атаку. Не решали в этой
итерации; если станет проблемой — можно поднять burst или считать лимит
по IP+первым байтам ClientHello, а не по голому IP.

## 2026-07-06 — Anti-replay кэш для msg1

**Что делали:** добавили кэш эфемеральных pubkey клиента (`replay.go`),
защищающий от повторной отправки ранее перехваченного (успешного) msg1.

**Что получилось:**
- Проверка стоит ПОСЛЕ успешной psk-аутентификации в `serverHandshake` —
  мусор и неверный psk кэш не засоряют, что и было целью дизайна.
- Простая структура: `map[[32]byte]time.Time` + мьютекс, окно 2 минуты,
  ленивая чистка протухших записей при каждой проверке — без bloom-filter
  и без фонового тикера (осознанно, см. `ponytail:`-комментарий в
  replay.go про O(n) чистку).
- 3 юнит-теста на сам кэш (дубликат/разные ключи/истечение окна — окно
  параметризовано, чтобы тест на истечение не спал 2 минуты, а 20/40мс).
- Интеграционный тест (`TestServerHandshakeRejectsReplay`): один и тот же
  валидный msg1 отправлен серверу дважды — первый раз проходит, второй
  отклоняется, `consumed` непустой (есть что отдать в fallback).
- Ручная проверка на реальных бинарниках: легитимный трафик и bad-psk
  fallback по-прежнему работают после того, как кэш вплетён в
  `cmdServer`/`serveConn`; один и тот же сырой HTTP-зонд отправлен на
  порт сервера дважды подряд — оба раза корректно ушли в transparent
  proxy на `dest` (что и ожидалось: мусор никогда не попадает в кэш, так
  что повтор мусора ведёт себя идентично первому разу).

**Что не получилось / пришлось поправить:**
- Обнаружился нюанс с `net.Pipe` в интеграционном тесте: если горутина
  клиента после записи msg1 не читает ответ сервера, `conn.Write(msg2)`
  внутри `serverHandshake` блокируется навсегда (peer не читает) —
  словили бы deadlock на самом первом (успешном) прогоне. Поправили: в
  тестовой горутине после записи msg1 явно вычитывается 48-байтовый
  ответ, прежде чем закрывать соединение.
- Замену реального бинарного захвата трафика (tcpdump/socat) для
  ручной demo-проверки повтора решили не делать — интеграционный тест
  уже детерминированно и точно проверяет именно это свойство на уровне
  `serverHandshake`; ручная проверка на бинарниках сосредоточилась на
  том, что не ловится юнит-тестами (реальные сокеты, реальные флаги,
  что кэш действительно передаётся через `cmdServer`→`serveConn`).
